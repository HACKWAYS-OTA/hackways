# Programs and ambassador applications

Global-backend owns programs, applications, private review and result publication.
Public-web markets the ambassador program. Core-web owns applicant pages. Admin-web
owns privileged program configuration and review. Existing six-service boundaries
are preserved; no extra backend, queue or dependency is introduced.

## Persistence and security

Migration 000025 adds programs, program_applications, program_releases and
program_activity. It seeds the real user-approved ambassador configuration. Queries
are generated by sqlc from db/queries/programs.sql. Downgrade refuses to discard
application, release or activity data. It has not been executed against production.

Programs have content and review revisions. Applications are unique per program /
user and transition from draft to submitted or withdrawn. Submitted answers retain
a question snapshot. Admin lists exclude unsubmitted drafts. Reviewer notes and
internal decisions are never selected by the applicant projection; own-record
queries are keyed by authenticated user rather than client-supplied user IDs.
Verified sessions, backend age/field/domain validation and same-origin checks gate
writes. Admin endpoints require the dedicated platform-admin session, grant and
daily OTP. Personalized responses are private/no-store.

All writes lock the program first, then the application where applicable, within a
transaction with a 2-second statement timeout. Revisions prevent stale overwrites.
Release locks the same program against concurrent submissions/reviews, requires
pending count zero and an exact reviewed count/revision, and publishes only complete
submitted decisions. Durable request key plus payload hash makes retries idempotent;
a changed payload with a reused key conflicts. Published decisions cannot be edited.
Submission writes a `program_application_received` email to the existing transactional
outbox inside the same transaction. Release atomically publishes the eligible decisions
and inserts one `program_results_released` notice per active verified applicant.
Repeated submit/release requests cannot create duplicate messages. Private decisions
and reviewer notes never enter email payloads; notices link to the authenticated
application. The bounded ACS worker rechecks recipient ownership, verified email,
account state and publication before dispatch. Withdrawal supersedes pending notices.
Ambassador confirmation copy includes the user-announced end-of-November result window;
this is an editorial deadline, not a new automatic release scheduler.

## API

Public base `/api/v1/programs`:

- GET `/`: open/closed programs, bounded pagination.
- GET `/{slug}`: program content, questions and current accepting status.
- GET `/{slug}/application`: authenticated user's own draft/submission/result.
- POST `/{slug}/application`: save a draft using program/application revisions.
- POST `/{slug}/application/submit`: validate and submit the current draft.
- POST `/{slug}/application/withdraw`: explicitly withdraw an owned application.

Admin base `/api/v1/admin/global/programs`:

- GET/POST `/`: list or create programs.
- GET/POST `/{slug}`: read or update settings with content revision.
- GET `/{slug}/applications`: search/filter/paginate submitted or withdrawn records.
- GET `/{slug}/applications/{id}`: private profile, answers and reviewer state.
- POST `/{slug}/applications/{id}/decision`: private revision-checked review.
- POST `/{slug}/release`: preview-guarded result publication and release history.

Question kinds: text, long_text, url, choice. Maximum 10 extra questions, 20 choices,
5,000 characters per answer. Website rules accept HTTPS URLs, no embedded userinfo,
and an optional configured exact hostname or its subdomains. A rule for linkedin.com
accepts www.linkedin.com and rejects linkedin.com.evil.example. Production origin
remains the existing canonical hackways.in; localhost ports are development-only.

program templates. Europe transport uses protected configuration outside Git.

The existing mandatory Go suite includes real PostgreSQL coverage for authorization,
age, configurable domains, draft/submit/retry, private decisions, release conflicts,
publication idempotency, ownership, withdrawal, confirmation/notification deduplication
and absence of result notifications before release. Run
against an explicit isolated `_test` database. See the worklog for commands actually
executed and verification limitations. Nginx routing is prepared in source only;
no production migration or deployment has been performed for this work.

## Ambassador contact requirements

Final submission requires a LinkedIn HTTPS profile (exact linkedin.com or subdomain),
a WhatsApp number normalized to E.164, city, name, introduction and event proposal.
Incomplete drafts remain saveable. Age stays a backend eligibility check, not a
promotional headline. Migration 26 updates only the original seeded copy; administrator
custom text is preserved.
